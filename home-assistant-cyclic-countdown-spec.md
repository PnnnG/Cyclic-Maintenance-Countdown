# Техническое задание: Cyclic Maintenance Countdown для Home Assistant

## 1. Задача

Разработать с нуля UI-first решение для Home Assistant, предназначенное для циклического бытового обслуживания: замена фильтров, добавление бактерий в септик, пополнение соли, чистка контейнеров и аналогичные действия.

Решение должно состоять из:

1. backend-интеграции Home Assistant, которая хранит задачи, рассчитывает сроки, переживает перезапуски и отправляет уведомления;
2. Lovelace-карточки с двумя переключаемыми стилями;
3. полноценного визуального редактора карточки и задачи без обязательного YAML.

Главный сценарий:

1. Пользователь добавляет карточку на dashboard.
2. В визуальном редакторе вводит название, выбирает иконку, задаёт цикл в днях и дату последнего выполнения либо начинает цикл сегодня.
3. При необходимости включает обратное направление прогресса, задаёт warning-период и уведомления.
4. Карточка ежедневно показывает оставшиеся дни и визуальный прогресс.
5. Пользователь отмечает обслуживание выполненным.
6. Новый срок рассчитывается от фактической даты выполнения, а не от старого дедлайна.

Это не список дел, не календарь, не sidebar-панель и не универсальный task manager. Один экземпляр карточки отображает одну циклическую задачу обслуживания.

## 2. Визуальные референсы

В папку проекта вместе с этим ТЗ будут положены два исходных скриншота. Они являются источником истины для общей композиции, пропорций и визуального характера. Не копировать из них жёстко заданные цвета: карточка должна корректно наследовать светлую и тёмную темы Home Assistant.

### Стиль A — `bar`

Основан на первом скриншоте:

- вытянутая карточка-капсула с большим радиусом скругления;
- слева отдельная мягко выделенная плитка с иконкой;
- в основной области — жирное название и менее контрастная метаинформация;
- справа — крупное целое число оставшихся дней и небольшая локализованная единица измерения;
- под текстом — тонкий горизонтальный progress bar;
- progress bar не должен доходить до правого края карточки: справа необходимо сохранить отдельную визуальную колонку под крупное число дней;
- вместо процента из референса основным значением должны быть дни;
- число дней должно быть заметно крупнее текста и по выразительности приближаться ко второму референсу;
- допустим аккуратный тематический градиент внутри заполненной части шкалы, но без кислотных цветов.

Рекомендуемая метаинформация: `Последнее выполнение: 2 авг., 19:40`. Если места мало, использовать короткий локализованный формат даты без времени.

### Стиль B — `fill`

Основан на втором скриншоте:

- спокойная прямоугольная карточка с большим радиусом скругления;
- слева квадратная плитка с иконкой;
- по центру — название и дата следующего срока;
- справа — очень крупное число оставшихся дней и небольшая локализованная единица;
- прогресс реализовать как ненавязчивую заливку фона самой карточки;
- граница заливки должна двигаться по горизонтали согласно прогрессу, не ухудшая читаемость текста;
- заливка размещается под контентом и не должна выглядеть как отдельная яркая кнопка;
- при 0% фон остаётся базовым, при 100% заполнена вся полезная ширина карточки.

Рекомендуемая метаинформация: локализованная дата следующего срока, например `Вс, 23 авг.`.

### Общие требования к обоим стилям

- Переключение `bar` / `fill` выполняется в визуальном редакторе с живым preview.
- Не использовать круговые индикаторы.
- Карточка должна выглядеть нативно рядом со штатными Mushroom/Tile-карточками HA, но не зависеть от них.
- Использовать CSS-переменные Home Assistant: фон карточки, основной и вторичный текст, divider, warning/error/accent. Собственные fallback-значения допустимы.
- Поддержать светлую и тёмную темы, произвольный accent color и `card-mod` без обязательной зависимости от него.
- Не зашивать английское `DAYS`: единица должна локализоваться и корректно склоняться (`1 день`, `2 дня`, `5 дней`; аналогично для английского).
- На узкой карточке название обрезается многоточием, но число дней и статус не перекрываются.
- Целевые размеры для desktop/tablet: высота 96–124 px. На узком мобильном layout допустима высота до 144 px.
- Минимальная зона нажатия интерактивного элемента — 44×44 px.

## 3. Модель времени и расчёты

Отсчёт календарный, в днях, в локальной временной зоне Home Assistant. Для MVP часы и минуты не являются отдельной единицей периода.

Для каждой задачи хранить:

- `task_id`: стабильный UUID;
- `name`;
- `icon`: MDI-иконка;
- `interval_days`: целое число от 1 до 3650;
- `last_completed_date`: локальная календарная дата;
- `due_date`: `last_completed_date + interval_days`;
- `warning_days`: целое число от 0 до `interval_days`, по умолчанию `1`;
- настройки уведомлений;
- идентификатор текущего цикла и отметки уже отправленных уведомлений.

Расчёт значения:

```text
remaining_days = due_date - local_today
```

Примеры:

- срок через 13 дней → `13`;
- сегодня срок выполнения → `0`;
- срок был вчера → `-1`;
- просрочка не переносит срок автоматически и продолжает уменьшать значение: `-2`, `-3` и т. д.;
- выполнение просроченной задачи сегодня создаёт новый срок `today + interval_days`.

Не использовать время последнего изменения entity как начало цикла. После перезапуска Home Assistant даты и значение должны восстановиться без сдвига.

### Прогресс

Нормализованный прошедший прогресс:

```text
elapsed = clamp((interval_days - remaining_days) / interval_days, 0, 1)
```

В редакторе должна быть галочка `Обратное направление прогресса`:

- выключена: визуальный прогресс идёт от `0%` после выполнения к `100%` в день срока;
- включена: визуальный прогресс идёт от `100%` после выполнения к `0%` в день срока.

После наступления просрочки индикатор остаётся в своём крайнем положении, а отрицательное число продолжает изменяться. Направление влияет только на визуализацию, но не на календарный расчёт и уведомления.

## 4. Состояния задачи

Реализовать явную конечную модель состояний:

| Состояние | Условие | Отображение |
|---|---|---|
| `normal` | `remaining_days > warning_days` | Спокойный тематический фон, обычный прогресс |
| `warning` | `0 < remaining_days <= warning_days` | Мягкое жёлто-янтарное «дыхание» |
| `due` | `remaining_days == 0` | Стильное красно-коралловое «дыхание», возможно очень лёгкий zoom |
| `overdue` | `remaining_days < 0` | То же danger-состояние, число показывается со знаком минус |
| `just_completed` | кратко после успешного действия | Ненавязчивая success-реакция и обновлённый срок |

Если `warning_days = 0`, состояние `warning` отключается. Значение по умолчанию — `1`, то есть жёлтое дыхание начинается за один календарный день до срока.

### Анимации

- Warning: плавная пульсация янтарной полупрозрачной заливки/ореола, цикл примерно 2.8–3.4 секунды.
- Due/overdue: плавная пульсация приглушённой кораллово-красной заливки. Не использовать чистый `#ff0000` и не закрашивать карточку сплошным непрозрачным красным.
- Допустимый zoom в danger-состоянии: максимум примерно `1.008–1.012`, без скачка layout и обрезания соседних карточек.
- Предпочтительный эффект — «дыхание» фонового overlay; число и текст не должны мигать и терять читаемость.
- При `prefers-reduced-motion: reduce` отключить zoom и циклическое мигание, сохранив статический warning/danger tint и понятный статус.
- Анимации должны использовать `opacity` и `transform`, не вызывать постоянный reflow и не нагружать dashboard.

## 5. Действия пользователя

### Выполнение задачи

Основное действие — `Выполнено сейчас`.

- По умолчанию tap по карточке открывает more-info выбранной sensor entity, hold открывает компактное подтверждение выполнения с названием задачи, текущим сроком и кнопками `Выполнено` / `Отмена`, double tap ничего не делает.
- В редакторе можно отключить подтверждение.
- После подтверждения backend атомарно сохраняет `last_completed_date = local_today`, пересчитывает `due_date`, начинает новый цикл и сбрасывает флаги уведомлений.
- UI должен обновиться сразу, но при ошибке backend обязан откатить optimistic update и показать понятное сообщение.
- Повторный быстрый tap не должен выполнить действие дважды.

Дополнительно зарегистрировать action/service `cyclic_countdown.complete`, чтобы задачу можно было завершать из автоматизаций и скриптов HA.

### Редактирование и удаление

- Из редактора Lovelace пользователь может изменить параметры выбранной задачи.
- Изменение `interval_days` должно показывать, как изменится `due_date`, до сохранения.
- По умолчанию при смене периода сохранить `last_completed_date` и пересчитать срок от неё.
- Удаление задачи — только с подтверждением; карточки, ссылающиеся на удалённую задачу, показывают понятное неинтерактивное состояние `Задача не найдена`. Исправление ссылки выполняется через штатное редактирование карточки в Home Assistant.

## 6. Визуальный редактор карточки

Использовать штатный механизм graphical card configuration Home Assistant (`getConfigElement` либо актуальный эквивалент). Не требовать ручного YAML для базового сценария.

Редактор разделить на логические секции.

### Задача

- выбор существующей задачи;
- `Создать новую задачу`;
- название — обязательная строка;
- иконка — штатный HA icon selector;
- период в днях — обязательное целое число, минимум `1`;
- начало цикла: `Сегодня` или выбранная дата последнего выполнения;
- preview рассчитанной даты следующего срока;
- количество warning-дней, default `1`.

### Внешний вид

- переключатель стиля с двумя наглядными миниатюрами: `Полоса` (`bar`) и `Заливка карточки` (`fill`);
- галочка `Обратное направление прогресса`;
- необязательный accent color; по умолчанию цвет темы;
- переключатель показа вторичной строки;
- выбор вторичной строки: `Дата срока` или `Последнее выполнение`;
- live preview состояний `normal`, `warning`, `due`, `overdue` без изменения реальной задачи.

### Поведение

- подтверждать выполнение — включено по умолчанию;
- tap, hold и double-tap настраиваются независимо;
- для каждого жеста доступны `Выполнить`, `Подробнее` и `Нет действия`;
- значения по умолчанию: tap — `Подробнее`, hold — `Выполнить`, double-tap — `Нет действия`.

### Уведомления

- галочка `Отправлять уведомления`;
- multi-select доступных целей уведомлений с понятными именами устройств;
- пользовательский заголовок, необязательный;
- пользовательский текст сообщения, обязательный при включённых уведомлениях;
- выбор событий: `При входе в warning` и `В день срока`; оба доступны независимо;
- показать preview итогового сообщения;
- поддержать безопасные подстановки `{name}`, `{days}`, `{due_date}`; не исполнять произвольный Jinja в MVP;
- кнопка `Отправить тест` — приоритет P1.

Если интеграция не установлена или не загружена, редактор должен сообщить об этом прямо и дать короткую инструкцию, а не падать с JavaScript-ошибкой.

## 7. Уведомления

Уведомления выполняются backend-интеграцией, а не браузером и не открытой карточкой.

Требования:

- перечислять доступные notify-цели через backend API и показывать пользователю дружественные имена;
- поддержать современные `notify` entity и совместимые mobile-app notify targets, реально доступные в установленной версии HA;
- отправлять сообщение во все выбранные цели;
- warning-уведомление отправляется один раз при первом входе текущего цикла в warning-окно;
- due-уведомление отправляется один раз за цикл при `remaining_days <= 0`: в день срока либо один раз после запуска, если Home Assistant был выключен в этот день;
- в MVP не отправлять ежедневные повторные сообщения в просрочке;
- хранить отметки доставки по `cycle_id + event`, чтобы перезапуск HA или повторное планирование не создавали дубликаты;
- если HA был выключен в момент триггера, после запуска выполнить reconciliation: отправить актуальное ещё не отправленное уведомление один раз;
- сбой одной цели не должен мешать отправке остальным; ошибку записать в лог и показать диагностическую информацию без утечки содержимого приватных уведомлений;
- доставка best-effort: если хотя бы одна цель приняла событие, общий marker цикла сохраняется, а неуспешные цели автоматически не повторяются в этом цикле; если не приняла ни одна цель, marker не ставится и следующая reconciliation может повторить попытку;
- удалённая или недоступная notify-цель помечается в редакторе как недоступная и не удаляется молча из настроек.

Планирование должно учитывать смену временной зоны, переходы DST и изменение системной даты. Для дневного countdown достаточно пересчёта в локальную полночь и при старте интеграции.

## 8. Архитектура

### Обязательное разделение ответственности

`custom_components/cyclic_countdown`:

- единственный источник истины для задач и дат;
- versioned persistence через штатный `homeassistant.helpers.storage.Store` либо более подходящий актуальный публичный API HA;
- config flow для первичной установки через UI, без обязательного `configuration.yaml`;
- sensor entity на каждую задачу;
- service/action `complete`;
- WebSocket API для списка, создания, редактирования, удаления, завершения задач и получения notify-целей;
- календарное планирование и отправка уведомлений;
- миграции схемы хранилища.

Frontend `cyclic-countdown-card`:

- Lit + TypeScript;
- только отображение, взаимодействие и visual editor;
- не хранит канонические даты в local storage;
- подписывается на состояния HA и обновления задач;
- использует CSS custom properties и Shadow DOM;
- отрисовывает оба визуальных режима из одной модели состояния.

### Sensor entity

Для каждой задачи создать сущность вида `sensor.<slug>_countdown` со стабильным `unique_id`, основанным на UUID, а не на изменяемом названии.

Рекомендуемое состояние:

```text
state: remaining_days
unit_of_measurement: d
```

Минимальные атрибуты:

```yaml
task_id: <uuid>
name: Бактерии
icon: mdi:bacteria
interval_days: 14
last_completed_date: "2026-08-10"
due_date: "2026-08-24"
remaining_days: 14
elapsed_progress: 0.0
phase: normal
warning_days: 1
```

Не задавать `state_class`: отрицательные значения здесь являются состоянием срока, а не измерением для long-term statistics.

### WebSocket/API-контракт

Имена могут быть уточнены по актуальным соглашениям HA, но функционально нужны операции:

- `cyclic_countdown/tasks/list`;
- `cyclic_countdown/tasks/create`;
- `cyclic_countdown/tasks/update`;
- `cyclic_countdown/tasks/delete`;
- `cyclic_countdown/tasks/complete`;
- `cyclic_countdown/notification_targets/list`;
- `cyclic_countdown/notifications/test` — P1.

Создание, изменение и удаление требуют admin permission. Выполнение задачи доступно авторизованному пользователю с правом управления соответствующей entity. Все payload валидировать на backend.

### Надёжность

- Запись выполнения должна быть атомарной.
- Использовать стабильный UUID и versioned schema.
- Предусмотреть миграцию данных при изменении формата.
- Не создавать polling раз в секунду: дневные значения пересчитываются по расписанию и при значимых событиях.
- После reload интеграции не должно оставаться старых таймеров или дублированных listeners.
- Удаление задачи корректно удаляет её entity из entity registry либо выполняет документированное безопасное отключение по правилам актуальной версии HA.

## 9. Конфигурация Lovelace

Визуальный редактор является основным способом настройки. YAML нужен только как переносимый/диагностический формат.

Пример минимальной конфигурации:

```yaml
type: custom:cyclic-countdown-card
task_id: 2f96074a-8a53-4b35-bb80-d8ce560cf888
style: bar
reverse_progress: false
confirm_complete: true
secondary_info: last_completed
```

Пример второго стиля:

```yaml
type: custom:cyclic-countdown-card
task_id: 2f96074a-8a53-4b35-bb80-d8ce560cf888
style: fill
reverse_progress: true
confirm_complete: true
secondary_info: due_date
```

Настройки самой задачи и уведомлений хранятся в backend и не дублируются в каждой карточке. В Lovelace хранятся только presentation/interaction settings и `task_id`.

## 10. Локализация и доступность

MVP должен включать русский и английский языки.

- Использовать язык и locale Home Assistant для дат, чисел и plural forms.
- Не собирать даты вручную конкатенацией строк.
- Добавить ARIA-label, описывающий название, оставшиеся/просроченные дни и доступное действие.
- Все действия доступны с клавиатуры.
- Видимый focus ring обязателен.
- Контраст текста и ключевых элементов — не ниже WCAG AA в типовых светлой и тёмной темах.
- Цвет не должен быть единственным носителем состояния: warning/due/overdue отражаются также текстом/иконкой/ARIA-описанием.
- Поддержать `prefers-reduced-motion`.

Допускается изменить структуру согласно актуальным рекомендациям Home Assistant и HACS, сохранив разделение backend/frontend. Итоговая установка должна быть максимально близка к одной HACS-установке. Если безопасная автоматическая регистрация frontend resource невозможна на поддерживаемых версиях HA, документировать один короткий шаг добавления ресурса и не использовать приватные нестабильные API ради его автоматизации.

## 12. Тестирование

### Backend

Покрыть тестами:

- расчёт дат и `remaining_days` для future/due/overdue;
- выполнение вовремя и после просрочки;
- изменение периода;
- локальную полночь, timezone и DST;
- восстановление после перезапуска;
- миграцию storage schema;
- отсутствие дублей уведомлений;
- catch-up уведомлений после простоя;
- частичный сбой нескольких notify-целей;
- права доступа и валидацию WebSocket/service payload.

### Frontend

Покрыть тестами:

- оба стиля и оба направления прогресса;
- четыре основных состояния;
- отрицательные дни;
- pluralization RU/EN;
- узкую/широкую карточку;
- визуальный редактор и live preview;
- подтверждение и защита от двойного выполнения;
- missing task/integration и backend error;
- reduced motion.

До stable-релиза добавить visual regression snapshots для `bar` и `fill` в `normal`, `warning` и `overdue`, отдельно для светлой и тёмной темы. Для beta обязательна ручная проверка той же матрицы на реальном Home Assistant с фиксацией результата в release checklist.

### Проверки перед выпуском

- Python tests;
- frontend unit tests;
- typecheck и lint;
- `hassfest` для custom integration;
- HACS validation;
- ручная проверка на минимально поддерживаемой версии HA и на последней stable;
- отсутствие ошибок в browser console и HA logs при добавлении, редактировании, выполнении и reload интеграции.

Целевая совместимость первой версии: Home Assistant Core 2026.7+; если используемый публичный API требует более новую версию, явно зафиксировать минимальную версию в manifest и README.

## 13. Приоритеты

### P0 — MVP, обязательно

- backend-интеграция с UI config flow и persistent storage;
- создание, изменение и удаление одной или нескольких задач;
- цикл в календарных днях от фактического выполнения;
- `0`, отрицательные дни и отсутствие автоматического переноса просрочки;
- sensor entity на задачу и action `complete`;
- Lovelace-карточка;
- оба стиля `bar` и `fill`;
- нормальное и обратное направление прогресса;
- `normal`, `warning`, `due`, `overdue`;
- warning days с default `1`;
- аккуратные yellow/red breathing animations и reduced motion;
- визуальный редактор с live preview;
- выбор notify-целей и пользовательский текст;
- тестовое уведомление из текущих, в том числе несохранённых, значений;
- независимые действия tap, hold и double-tap;
- optional notification title и безопасные placeholders `{name}`, `{days}`, `{due_date}`;
- однократные warning/due уведомления без дублей;
- русский и английский интерфейс;
- базовые unit/integration/frontend tests;
- документация установки и использования.

### P1 — сразу после MVP

- undo последнего выполнения через snackbar в течение короткого времени;
- расширенная настройка цветов и интенсивности анимации;
- импорт/экспорт задачи;
- повтор уведомления через настраиваемый интервал при просрочке, выключенный по умолчанию.

### P2 — не блокирует релиз

- история выполнений и статистика соблюдения сроков;
- недели/месяцы как отдельные календарные единицы;
- группы/список нескольких задач в одной карточке;
- snooze/skip cycle;
- reusable themes/presets;
- действия уведомления `Выполнено` через companion app;
- отдельный dashboard overview.

## 14. Вне scope MVP

- sidebar-панель;
- shopping list, chores/to-do manager, subtasks и исполнители;
- cron-расписания и правила вида «каждый второй вторник»;
- зависимость от MQTT, Node-RED, AppDaemon или внешнего сервера;
- обязательные helper entities и ручные template sensors;
- круговой progress indicator;
- полноценный журнал обслуживания;
- произвольное выполнение Jinja из пользовательского текста уведомлений.

## 15. Acceptance criteria MVP

MVP считается готовым только если выполняются все пункты:

1. На чистой поддерживаемой установке HA пользователь устанавливает интеграцию, добавляет её через UI и создаёт карточку без редактирования YAML.
2. В редакторе можно создать задачу `Бактерии`, указать `14` дней, выбрать дату последнего выполнения и увидеть корректную дату срока.
3. При дате срока через 13 дней карточка показывает `13`, а не процент и не часы.
4. В день срока показывается `0`; на следующий календарный день — `-1`; карточка не начинает новый цикл сама.
5. После `Выполнено сейчас` срок становится `today + 14 days`, даже если задача была просрочена.
6. Даты и состояние не меняются после restart/reload HA, кроме ожидаемого перехода календарного дня.
7. В стиле `bar` отображаются иконка, название, вторичная строка, крупное число дней и отдельная горизонтальная шкала, заканчивающаяся до колонки числа.
8. В стиле `fill` те же данные отображаются без отдельной шкалы, а прогресс читается по мягкой фоновой заливке карточки.
9. При переключении reverse progression визуально меняется `0→100` на `100→0`, но число дней и due date остаются прежними.
10. При `warning_days = 1` карточка входит в жёлтое состояние ровно за один календарный день до срока.
11. При `0` и отрицательном значении включается мягкое danger-дыхание; чистый ярко-красный фон и мигающий текст отсутствуют.
12. При reduced motion состояние остаётся различимым, но циклическая анимация отключена.
13. Выбранные notify-цели получают заданный текст при warning/due согласно настройке.
14. Reload/restart HA не приводит к повторной отправке уже отправленного уведомления текущего цикла.
15. Завершение задачи запускает новый notification cycle.
16. Оба стиля корректно работают в светлой и тёмной теме и при ширине мобильной колонки без наложения текста.
17. Русские формы `день/дня/дней`, даты и английская локализация отображаются корректно.
18. Ошибка backend, удалённая задача или недоступная notify-цель дают понятное UI-сообщение и не ломают dashboard.
19. Все обязательные автоматические проверки проходят, а в HA logs и browser console нет необработанных ошибок.

## 16. Definition of done

- Исходники backend и frontend находятся в одном документированном репозитории.
- Репозиторий содержит готовый production bundle карточки, но сгенерированный bundle не подменяет исходный TypeScript.
- Есть пошаговый README: установка, добавление интеграции, создание первой задачи, добавление карточки, уведомления, обновление и удаление.
- Есть скриншоты обоих режимов и основных состояний.
- Версии и миграции задокументированы.
- Создан первый versioned release, пригодный для установки согласно выбранной схеме HACS.

Перед реализацией сверить публичные API с актуальной документацией Home Assistant. Не использовать приватные frontend/backend API без документированной причины и fallback. При неоднозначности визуальных деталей ориентироваться на приложенные референсы и требования из раздела 2, сохраняя нативность для темы Home Assistant.
